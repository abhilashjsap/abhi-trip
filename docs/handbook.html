01

Overview

AbhiTrip turns five form fields into a full trip dossier. Enter a destination, a budget, a headcount, and how many days you've got — the AI fills in everything else.

It's a single-user, password-gated hobby app: one person's trip planner, not a multi-tenant product. There's no sign-up, no billing, no account system — just a shared password and a form.

A generated trip includes:

Itinerary

Day-by-day plan with morning/afternoon/evening activities, editable inline and regeneratable one day at a time.

Budget breakdown

Flights, accommodation, food, transport, and activities as line items, with a per-person toggle.

Attractions + map

5–8 real places with photos (Unsplash) and pins on an OpenStreetMap view.

Weather

Historical monthly averages plus a real 7-day forecast layered on top for near-term trips.

Currency & exchange

Local currency info with a live FX rate substituted in over the model's guess.

Beware of

Destination-specific scams, safety notes, and cultural pitfalls.

Food, shopping & packing

Local dishes with per-meal cost estimates, souvenirs, and a climate-appropriate packing list.

Trip chat

A floating Q&A widget grounded in that specific trip's content — ask it anything about the plan.

PDF export & sharing

Server-rendered PDF download, and a shareable read-only link that bypasses the password gate.

02

Architecture

A React SPA talking to a handful of Vercel serverless functions, plus several external APIs it calls straight from the browser. Which path a call takes depends on one thing: whether a secret needs to stay hidden.

The main generation request

Submitting the trip form runs a small pipeline, not one call: a cheap feasibility check on the budget (small model), then — if it passes — the main plan generation (large model), streamed token-by-token back to the browser so the loading screen shows live progress instead of a static spinner.

The response is constrained by a JSON responseSchema, not just a "please return JSON" instruction — Gemini validates the shape (required fields, types, array bounds, string length caps) server-side before it ever reaches the client. Structural validity is enforced this way; content quality is still down to prompt wording.

After the JSON comes back, two more enrichments run client-side: a live FX rate overwrites the model's currency guess (Frankfurter), and attraction photos are fetched (Unsplash) and merged in.

Where the code lives

  • src/components/ — one file per section of the result page (Itinerary, Weather, BewareOf, TripChat, …)

Changing any of these requires a redeploy — Vite bakes VITE_-prefixed values into the build at compile time, so saving a new value in Vercel's dashboard alone doesn't touch the already-built, already-live JS.
06

Data & storage

There's no database. State lives in two places, and neither is durable in a way that matters for this kind of app.

Browser localStorage

  • Current trip — the last generated trip, restored on reload so refreshing the page doesn't lose it.
  • Trip history — every generated trip, so past plans can be revisited.
  • Daily request count — how many calls have gone out to each Gemini model today, reset at midnight, backing the "trips left today" estimate. It tracks requests, not tokens — the free tier's actual limit is a request count, and a token-based estimate here previously showed a wildly wrong number.

Upstash Redis

The only server-side persistence. A shared trip is the full trip JSON stored under a random 10-character key with a 90-day TTL — nothing more structured than that, since the only operations needed are "store one trip" and "fetch one trip by id."

07

Key decisions

The parts of the design that aren't obvious from reading the code — why it works this way, not just that it does.

Schema-enforced JSON, not "please return JSON"
Why: loose JSON-mode output truncated or came back malformed often enough to be a real problem. A Gemini responseSchema validates shape server-side — required fields, types, array/string length bounds — so the model can no longer return something structurally wrong, only content that's inaccurate.
Streaming generation with three layered failure guards
Why: the main plan generation takes long enough that a static spinner felt broken, so it streams. That streaming pipe also turned out to be the fix for a nastier problem: Gemini would occasionally get stuck in a decoding loop, ballooning one field to tens of thousands of repeated characters. Three checks now run on every chunk — an exact-repetition detector, a hard cap on how long any single JSON string is allowed to get, and a check that the model actually signaled a clean finish rather than just going silent. Any of the three aborts and retries automatically, almost always invisibly to the user.
Native PDF generation, not a DOM screenshot
Why: the original approach (html2canvas + jsPDF) broke in four different ways across one session — a page-size cap that silently corrupted pagination, a horizontally-scrolling section getting clipped out, a CSS animation replaying mid-capture and washing out the colors, and page breaks landing mid-card. It was rewritten from scratch: a server-side @react-pdf/renderer document built from the trip's actual data, not a picture of whatever happened to be on screen.
The main model has moved twice
Why: it started on a preview-tier model with an unusually tight 20-requests/day quota and a decoding-instability streak that didn't clear up with prompt or temperature tuning. The next model tried turned out to already be deprecated for new API keys — Google's own error named its replacement directly, which is what's running now. The model name is expected to need revisiting again if either problem resurfaces; it isn't treated as a settled choice.
The trip chat uses the small model, deliberately
Why: conversational Q&A doesn't need the large model's structured-output budget, and it draws from a separate daily quota pool — keeping chat traffic off the same tight allowance as full trip generation.
08

Limitations

Worth knowing before explaining this to someone, so a rough edge doesn't read as a bug.

  • The daily AI quota is genuinely tight. The free tier caps requests per day per model, and a single "Generate" click can cost more than one request if a retry fires — the quota can run out mid-session on a busy day.
  • Gemini occasionally returns a 503 ("high demand"). This is transient and outside the app's control; it's retried automatically with backoff and surfaces a plain "try again shortly" message if all retries fail.
  • The password gate is a deterrent, not security. It's a client-bundled value, visible to anyone who inspects the built JS. Fine for a private link shared with family; not a real access-control boundary.
  • Weather comes in two flavors that don't always agree. The monthly grid is historical averages; the live strip above it is today's actual forecast. They can legitimately disagree on any given week — that's expected, not a data error.
  • No real flight pricing exists as a free option. Every previously-free flight-fare API (Amadeus's self-service tier, Kiwi's Tequila API) has closed off free access; flight estimates remain an LLM guess rather than a live fare lookup.
09

Deployment

Vercel, connected directly to the GitHub repo. There's no separate staging environment.

Every push to main triggers a fresh build and deploy automatically. api/*.js files are picked up as Vercel Functions with no separate server process to manage — each one exports a Web-standard fetch(request) handler.

git push origin main
> Vercel detects the push, builds (`vite build`), deploys
> api/gemini.js, api/pdf.js, api/share.js become live serverless functions
> static assets (the built SPA) are served from Vercel's edge
Local development only runs the frontend (vite dev) — the api/ functions don't execute under plain Vite, so anything touching Gemini, PDF export, or sharing can only be fully tested against the real deployment.
